# Infraestrutura de Contas de Teste e Ambiente de QA — Serviços Já

Este documento descreve a arquitetura, personas, regras de isolamento, procedimentos de reset e matriz de permissões das contas de teste do **Serviços Já** (Sprint P15.1).

---

## 1. Princípio Fundamental de Segurança

> [!IMPORTANT]
> **Zero Bypass de Segurança**  
> As contas de teste utilizam **exatamente as mesmas regras de autenticação, RLS, autorização e políticas de segurança** das contas reais de produção. É expressamente proibido criar condicionais como `if (isTestUser) allowEverything()`.
> 
> Não existe nenhuma conta "Master User" ou "Master Role". As contas de teste mantêm o princípio do menor privilégio (`client`, `provider` ou `admin`).

---

## 2. Identificação das Contas de Teste (`qa_test_accounts`)

A identificação das contas de teste é realizada no banco de dados através da tabela dedicada `public.qa_test_accounts`:

```sql
CREATE TABLE public.qa_test_accounts (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id UUID UNIQUE NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  persona TEXT NOT NULL CHECK (persona IN ('client', 'provider', 'admin')),
  description TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())
);
```

### Vantagens da Arquitetura:
1. **Preservação do Domínio de Negócio:** Não altera a estrutura de `profiles` com flags mutáveis.
2. **Imutabilidade pelo Cliente:** Usuários comuns não conseguem se registrar ou se promover a contas de teste via frontend.
3. **Isolamento de Analytics:** A RPC `log_analytics_event` identifica automaticamente se o evento partiu de um `user_id` cadastrado em `qa_test_accounts` e sinaliza `is_test_event = true`.

## 3. Personas de Teste

| Persona | E-mail de Referência | Role | Finalidade no Ambiente de QA |
| :--- | :--- | :--- | :--- |
| **Cliente Teste** | `cliente.teste@servicosja.com` | `client` | Testar login, catálogo público, navegação de perfil, contatos e bloqueio de rotas privadas (`/provider`, `/admin`, `/analytics`). |
| **Prestador Teste** | `prestador.teste@servicosja.com` | `provider` | Testar onboarding, formulários, serviços, áreas de atendimento, upload/ordem do portfólio, preview, assinatura e solicitação de publicação. |
| **Admin Teste** | `admin.teste@servicosja.com` | `admin` | Testar moderação no painel `/admin`, revisão detalhada, aprovação (`published`), recusa com justificativa (`rejected`) e suspensão (`suspended`). |

## 5. Isolamento de Analytics de Teste

Eventos gerados por ações do **Cliente Teste**, **Prestador Teste** ou **Admin Teste** recebem a marcação server-side `is_test_event = true` na tabela `provider_analytics_events`.

As estatísticas comerciais dos prestadores reais ignoram eventos com `is_test_event = true`, garantindo **zero contaminação das métricas comerciais de produção**.

## 6. Procedimento Seguro de Reset de QA (`reset_qa_test_provider`)

Para permitir a re-execução dos testes do ciclo de vida a partir do estado inicial (`draft`), o sistema dispõe da RPC segura:

```sql
SELECT public.reset_qa_test_provider(p_provider_id);
```

### Regras de Proteção do Reset:
- Exige privilégios de Administrador (`is_admin()`).
- Valida se o `p_provider_id` pertence **comprovadamente** a uma conta cadastrada em `qa_test_accounts`.
- Se o ID pertencer a um prestador real de produção, a RPC interrompe a execução com a exceção:  
  *`Operação bloqueada: Apenas contas identificadas na infraestrutura de QA podem ser resetadas.`*

## 7. Gestão de Credenciais e Senhas de QA

As senhas das personas de QA **não são armazenadas no repositório** para garantir a segurança. Elas são gerenciadas localmente pelo responsável pelo ambiente de QA através de variáveis de ambiente.

### Comandos de Automação (CLI):
1. **Configuração e Sincronização Inicial de QA (`npm run qa:setup`):**
   ```powershell
   npm run qa:setup
   ```
   Cria/sincroniza idempotentemente as 3 personas oficiais (`cliente.teste@servicosja.com`, `prestador.teste@servicosja.com`, `admin.teste@servicosja.com`) nas tabelas `profiles`, `qa_test_accounts`, `provider_profiles` e `admin_users`.

2. **Redefinição Segura de Senhas (`npm run qa:reset-passwords`):**
   Para redefinir as senhas das 3 personas oficiais via Admin API do Supabase:
   ```powershell
   $env:SUPABASE_SERVICE_ROLE_KEY="sua_chave_service_role_aqui"
   $env:QA_CLIENT_PASSWORD="SuaNovaSenhaCliente123!"
   $env:QA_PROVIDER_PASSWORD="SuaNovaSenhaPrestador123!"
   $env:QA_ADMIN_PASSWORD="SuaNovaSenhaAdmin123!"
   npm run qa:reset-passwords
   ```

> [!CAUTION]
> - Nenhuma senha em texto puro ou chave `SUPABASE_SERVICE_ROLE_KEY` deve ser salva em arquivos versionados do Git.
> - O script `qa:reset-passwords` possui verificação de segurança que **recusa e aborta** qualquer tentativa de redefinir senhas de e-mails que não pertençam estritamente às personas oficiais registradas na tabela `qa_test_accounts`.
